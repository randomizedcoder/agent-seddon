# Increment 01 — Consensus gate (`provider = "consensus"`)

Goal: every final response is generated by the primary LLM and challenged by a
second LLM until the gate passes, bounded and fail-safe. Ships as a composing
`LlmProvider` — no proto change, no new seam — live-verifiable against Kimi
(generator) + GLM (critic) the day it lands.

## Shape

New module `crates/agent-providers/src/consensus.rs` (feature
`provider-consensus`), mirroring the composing-factory pattern of `router` /
`task-router` / verifier `ensemble`:

```rust
pub struct ConsensusProvider {
    generator: Arc<dyn LlmProvider>,   // by name via registry / route upstream
    critic:    Arc<dyn LlmProvider>,   // MUST be a different upstream; warn if same id
    cfg: GateCfg,
    observer: Option<Arc<dyn GateObserver>>,   // metrics decorator seam
}

pub struct GateCfg {
    pub max_rounds: u8,          // default 2, hard ceiling 5 (compile-time)
    pub gate: GateScope,         // Final (default) | EveryIteration
    pub on_exhaustion: Exhaustion, // DeliverWithNote (default) | Fail
    pub critic_max_tokens: u32,  // default 512
    pub max_alternatives: u8,    // default 3, hard ceiling 4
    pub rubric: Option<String>,  // operator-editable rubric text (prompt store)
}
```

`complete()`:
1. `generator.complete(req)` → candidate.
2. **Scope check**: if `candidate.tool_calls` is non-empty and `gate = Final`,
   return immediately — tool-call iterations are already gated by the verifier
   seam; double-gating them doubles cost for little value.
3. **Critic round** (bounded loop, `1..=max_rounds`):
   - Build a *fresh* critic request — never the generator's transcript
     (self-preference + sycophancy mitigation; also gives the critic its own
     stable prompt-cache prefix). Contents, each bounded like
     `agent-verifier/src/llm.rs` does (`MAX_*_CHARS`): the task (first user
     message), the candidate text, the rubric, and — when available — the last
     deterministic signals (validator outcome, verifier verdicts) which the
     critic may cite but not override.
   - Strict-JSON verdict, parsed with the `extract_json_object` discipline:

     ```json
     {"pass": bool,
      "issues": [{"severity": "...", "claim": "...", "evidence": "..."}],
      "alternatives": [{"option": "...", "summary": "...", "reconsider_when": "..."}],
      "confidence": 0.0}
     ```

     Hostile-input handling: clamp confidence to [0,1]; drop issues with empty
     `evidence` (evidence-free objections are noise per the debate literature);
     cap issues at 8 × 400 chars; cap alternatives at `max_alternatives` × 600
     chars, and drop alternatives with an empty `reconsider_when` (an option
     with no reconsideration trigger is an opinion, not a decision record);
     unparseable/erroring critic → **fail open** (deliver the candidate, count
     `critic_error`) — availability over the gate, same stance as
     `LlmVerifier`.
   - **Alternatives exit — don't force convergence on preference.** The rubric
     instructs the critic: when 2–3 approaches are genuinely defensible and the
     choice cannot be resolved with the information at hand (it would take more
     user input, or facts not yet known), do **not** raise issues to force a
     revision — set `pass: true` and fill `alternatives`, each stating the
     option, a one-paragraph summary, and **`reconsider_when`: what would need
     to become true for this option to be preferred** ("if X turns out to be
     unsupported…", "if the user needs Y…"). The gate then delivers the
     generator's choice with a bounded tail note —

     ```
     ## Open alternatives (recorded by the response gate)
     1. {option}: {summary}  Reconsider when: {reconsider_when}
     ```

     — so the options remain in the live context for the rest of the task, and
     surfaces the outcome as `gate_verdicts{outcome="alternatives"}`. The
     structured list also rides `GateOutcome` (observer surface) so increment
     02 can persist it to the digest ledger (`kind = alternatives`) without
     another LLM call, and increment 03 re-injects open alternatives across
     compactions. This is the constructive form of "disagreement is signal":
     defect-shaped disagreement loops (fix or rebut); preference-shaped
     disagreement is *recorded* instead of argued to capitulation.
   - `pass` → deliver. Otherwise **feedback injection** (DSPy-Refine semantics):
     append one user message to the generator request — *at the tail*, preserving
     the cached prefix — listing the issues verbatim plus the contract: "fix each
     issue, or rebut it with evidence; do not simply agree." Re-complete.
   - **No-progress exit**: if the new round's issue set (severity+claim,
     normalized) equals the previous round's, break — more rounds buy conformity
     risk at linear cost.
4. **Exhaustion**: `DeliverWithNote` appends a bounded system-visible note
   ("consensus not reached; N issues outstanding") so disagreement is *signal*,
   surfaced not swallowed; `Fail` returns an error (the agent-level retry/policy
   decides). Persistent disagreement is never silently accepted as agreement.

`capabilities()` = the generator's (the critic never serves the request);
`count_tokens` etc. delegate to the generator.

## Config

```toml
[provider]
backend = "consensus"

[provider.consensus]
generator = "kimi"        # route-upstream / provider names, registry-resolved
critic    = "glm"
max_rounds = 2
gate = "final"            # "final" | "every-iteration"
on_exhaustion = "deliver-with-note"
critic_max_tokens = 512
max_alternatives = 3
```

Registry: a composing factory (like `ensemble`) — `generator`/`critic` resolve
via `ctx.registry()?.build_provider(name, ctx)` or, when they name
`[[route.upstreams]]` entries, via `build_route_upstream` (secret-safe:
`api_key_file`/`api_key_env` only). Self-reference (`"consensus"`) rejected.
Critic == generator id is allowed but warned (defeats the different-family
mitigation).

The rubric defaults to a compiled binary checklist (correctness of claims ·
follows the stated task · no unverified assertions about code · commands/paths
plausible) and is operator-overridable via the prompt store
(`prompts/gate/rubric.md`), the lens-file pattern — versioned, editable without
rebuild (criteria drift mitigation).

## What this is not (yet)

- Not wired into a graph document — increment 04 re-expresses this provider as
  the `critic_gate` loop-until node; the engine and config carry over unchanged.
- Not per-`TaskMode` rubrics, not best-of-N + verifier ranking (sibling node,
  deferred), not a `--serve-*` seam (it is *made of* providers, which already
  serve).

## Tests / verification

Table-driven (`rstest`, all four classes + mandatory `adversarial_`), doubles via
`ScriptedProvider`:

- `positive_`: pass-first-round; fail-then-fix (2 rounds, feedback message
  present at tail); tool-call passthrough under `Final`.
- `negative_`: critic error → fail-open + counter; generator error propagates;
  `Fail` exhaustion returns Err.
- `corner_`: no-progress exit on identical issue set; critic returns prose with
  embedded JSON; `DeliverWithNote` note appended exactly once; alternatives
  exit — `pass` + alternatives delivers first-round with the tail note and no
  revise round; alternatives alongside `pass: false` (issues win, alternatives
  still recorded).
- `boundary_`: `max_rounds = 1`; issue list exactly at the cap; confidence 0/1;
  alternatives exactly at `max_alternatives`.
- `adversarial_`: confidence `NaN`/`-1`/`1e9` clamped; 10k issues / 1 MB claim
  capped; verdict text containing tool-call-like JSON or injection strings never
  executed, only quoted into feedback; critic "pass" with contradicting
  deterministic-red signal still blocked (conjunct); alternative with empty
  `reconsider_when` dropped; 100 alternatives / 1 MB summaries capped; injection
  strings inside `reconsider_when` quoted inert into the note.

Metrics (README table): `gate_rounds`, `gate_verdicts{outcome=pass|fixed|
alternatives|exhausted|critic_error}`, `gate_seconds{phase}`,
`gate_issues_total{result}`, `gate_alternatives_recorded_total`; span
`gate.round{round, verdict, issues}`.

Harness (README §Harness obligations): iai bench on verdict parse + issue-set
comparison with an Ir ceiling in `nix/checks/bench.nix`, set **after** the
optimization pass (run `nix run .#bench -- -p agent-providers`, take the
low-hanging fruit — e.g. reuse one serde buffer across rounds, avoid re-parsing
the rubric per round — record before/after Ir in the PR); live check: Kimi ×
GLM on a prompt seeded with a deliberate factual error → observe one revise
round; a second prompt with a genuine design trade-off → observe the
alternatives note. `nix flake check` green.
