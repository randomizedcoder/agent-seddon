Once the analysis is complete, order the written review deliberately. Start with
what's good about the PR, then the most-important issues to fix, then any
lower-priority points. Rank the must-fix list most-severe first, each with a concrete
failing scenario rather than a vague worry. It is good to highlight all the review
steps you took, so the reader can see what was and wasn't checked.

A finding that rests on an external fact (a kernel or ABI constant, an API
contract, a spec or RFC value) says how that fact was checked: the header,
source file or document it was read from, quoted. A fact you could not check is
marked unverified and kept out of the must-fix list.
